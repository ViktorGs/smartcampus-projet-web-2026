RÉSUMÉ — SmartCampus est une plateforme web dynamique de gestion académique destinée à une école d'ingénieurs. Elle centralise les interactions entre l'administration, les enseignants et les étudiants autour des cours, des inscriptions, des notes et des emplois du temps. Trois rôles utilisateurs (administrateur, enseignant, étudiant) accèdent à des fonctionnalités cloisonnées par un contrôle d'accès serveur (RBAC). Le projet répond au sujet « Projet Web dynamique 2026 — Sujet 2 » en respectant les contraintes imposées : base de données relationnelle (MySQL), backend PHP organisé en API REST, frontend HTML/CSS/JavaScript avec Bootstrap, et la mise en œuvre de plusieurs règles métier réalistes (capacité, prérequis, conflits d'emploi du temps, verrouillage des notes). Ce document présente les rôles utilisateurs, les fonctionnalités principales, les contraintes techniques, les technologies envisagées et la répartition prévisionnelle du travail entre les membres de l'équipe.
Nous attestons que ce travail est original, qu'il est le fruit d'un travail commun à l'équipe et qu'il a été rédigé de manière autonome.

    I. Objectif du document

    Ce document présente les spécifications fonctionnelles du projet SmartCampus, plateforme web dynamique de gestion académique développée dans le cadre du module « Projet Web dynamique 2026 — Sujet 2 ». Il s'adresse aux encadrants pédagogiques et constitue la première livraison du projet (livrable conception, dû le 28 mai 2026).

    Le lecteur y trouvera :

    • la description des rôles utilisateurs et de leurs permissions ;
    • les fonctionnalités principales envisagées (cœur du sujet et bonus) ;
    • les règles métier qui sécurisent les inscriptions, les notes et l'emploi du temps ;
    • les contraintes techniques imposées par le sujet et les technologies retenues ;
    • une première répartition prévisionnelle du travail entre les membres de l'équipe.

    IV. Contexte et problématique

    A. Contexte

    Les établissements d'enseignement supérieur gèrent un volume croissant d'informations académiques : inscriptions aux cours, suivi des notes, planification des cours, mais aussi communication entre l'administration, les enseignants et les étudiants. Ces informations sont aujourd'hui souvent dispersées entre plusieurs outils (intranet, tableurs, courriels), ce qui complique le suivi pédagogique et la prise de décision.

    Le présent projet s'inscrit dans le module « Projet Web dynamique 2026 » de l'ECE. Le sujet n° 2 demande la conception d'une plateforme web dynamique de gestion académique. Nous avons choisi comme contexte une école d'ingénieurs (organisation en filières, niveaux L1 → M2, semestres, crédits ECTS, groupes de TD).

    B. Problématique

    Comment concevoir une plateforme web unique, ergonomique et sécurisée, qui centralise la gestion académique d'une école d'ingénieurs en garantissant à chaque rôle utilisateur un accès strictement délimité à ses fonctionnalités, tout en appliquant des règles métier réalistes (capacité, prérequis, conflits horaires, verrouillage des notes) ?

    Cette problématique se décline en plusieurs sous-questions :

    • Quel modèle de données permet de représenter à la fois les étudiants, les enseignants, les cours, les inscriptions, les notes et l'emploi du temps sans duplication d'information ?
    • Comment cloisonner les droits de chaque rôle sans dépendre uniquement de l'interface graphique (sécurité côté serveur) ?
    • Comment garantir la cohérence des données face à des actions concurrentes (deux étudiants qui s'inscrivent en même temps à la dernière place d'un cours, par exemple) ?

    C. Public cible

    PublicBesoin principal
    ÉtudiantsConsulter rapidement leurs cours, leurs notes et leur emploi du temps ; s'inscrire ou se désinscrire d'un cours ; télécharger un relevé de notes.
    EnseignantsVoir les étudiants inscrits à leurs cours, saisir et valider les notes, consulter leur emploi du temps.
    Administration pédagogiqueGérer le référentiel (étudiants, enseignants, cours), planifier l'emploi du temps, suivre la réussite via des statistiques.

    V. Rôles utilisateurs

    La plateforme distingue quatre rôles. Le cloisonnement est imposé côté serveur (RBAC) — il ne dépend pas seulement de l'interface affichée.

    A. Visiteur

    • Consulter la page d'accueil et de connexion.
    • Créer un compte étudiant (inscription publique).
    • Aucun accès aux données académiques.

    B. Étudiant

    • Consulter le catalogue des cours et s'inscrire / se désinscrire (sous réserve des règles métier).
    • Consulter ses propres notes et calculs de moyenne, télécharger un relevé PDF.
    • Consulter son emploi du temps hebdomadaire.
    • Utiliser la messagerie interne avec ses enseignants.
    • Recevoir des notifications (note publiée, inscription validée…).

    C. Enseignant

    • Consulter la liste de ses cours et des étudiants inscrits.
    • Saisir, modifier et valider les notes (chaque note peut être verrouillée — elle devient alors définitive).
    • Consulter son emploi du temps.
    • Échanger des messages avec ses étudiants.
    • Restriction : un enseignant ne peut noter que les étudiants des cours qu'il encadre.

    D. Administrateur

    • Gérer le référentiel : étudiants, enseignants, cours, créneaux (CRUD complet).
    • Modérer les utilisateurs (activer / désactiver / supprimer).
    • Inscrire ou désinscrire un étudiant d'un cours en cas de besoin administratif.
    • Consulter des statistiques de réussite et de répartition.
    • Aucune restriction de visibilité (vue globale).

    B. Règles métier

    Le sujet exige plusieurs règles métier réalistes. Six règles sont prévues, toutes vérifiées côté serveur :

    1. Pas de double inscription — un étudiant ne peut s'inscrire deux fois au même cours.
    2. Contrôle de capacité — l'inscription est refusée si la capacité maximale du cours est atteinte.
    3. Prérequis académiques — l'inscription à un cours exige d'avoir validé (moyenne ≥ 10) les cours prérequis.
    4. Détection des conflits d'emploi du temps — un étudiant ne peut suivre deux cours qui se chevauchent ; deux créneaux ne peuvent pas être placés dans la même salle ou pour le même enseignant au même moment.
    5. Verrouillage des notes après validation — une note validée devient non modifiable et non supprimable.
    6. Restriction des actions selon les rôles — chaque action sensible vérifie le rôle et, pour l'enseignant, la propriété du cours.

    C. Cas d'utilisation principal — « S'inscrire à un cours »

    • Acteur principal : étudiant connecté.
    • Préconditions : l'étudiant est authentifié ; le cours existe et n'est pas archivé.
    • Scénario nominal :
      1. L'étudiant recherche / filtre un cours dans le catalogue.
      2. Il clique sur « S'inscrire ».
      3. Le serveur vérifie successivement : double inscription, capacité, prérequis, conflit d'emploi du temps.
      4. Si toutes les règles passent, l'inscription est enregistrée et une notification est créée.
    • Scénarios alternatifs : à chaque règle non respectée, l'inscription est refusée avec un message explicite (ex. « Ce cours est complet », « Prérequis non validés : INFO-203 », « Conflit d'emploi du temps avec MATH-202 »).

    VII. Contraintes techniques et technologies envisagées

    A. Contraintes techniques imposées par le sujet

    • Base de données relationnelle (MySQL ou équivalent).
    • Backend en PHP organisé en API REST, séparé du frontend.
    • Frontend en HTML / CSS / JavaScript, avec Bootstrap pour la mise en forme.
    • Validation des entrées côté client ET côté serveur.
    • Sécurité : sessions, jeton anti-CSRF, contrôle d'accès par rôle, requêtes préparées (anti-injection SQL), hashage des mots de passe.
    • Interface responsive (testée mobile et desktop).
    • Pas de framework lourd type Laravel ou Symfony (architecture maîtrisée, expliquable).

    B. Technologies retenues

    CoucheTechnologieJustification
    Base de données MySQL 8 (moteur InnoDB) Imposé par le sujet. InnoDB pour les clés étrangères et les transactions (cohérence lors des actions multi-tables).
    Backend PHP 8 (sans framework, mini-MVC maison) Imposé par le sujet. Un mini-noyau (≈ 6 classes) rend chaque mécanisme explicable en soutenance.
    Accès BDD PDO (requêtes préparées) Standard PHP ; protège contre les injections SQL.
    Frontend HTML5, CSS3, JavaScript ES modules Sans build (pas de Webpack / Vite) : modules ES natifs chargés dynamiquement.
    UI Bootstrap 5 + Bootstrap Icons Imposé par le sujet ; accélère la mise en forme et garantit le responsive.
    Graphiques Chart.js Léger, simple, sans dépendance ; suffisant pour les statistiques de l'admin.
    Génération PDF FPDF (PHP) Bibliothèque éprouvée pour produire des relevés de notes côté serveur.
    Serveur de dev WAMP (Apache + PHP + MySQL) sous Windows Environnement local standard pour les projets PHP à l'école.
    Versioning Git + GitHub Suivi des contributions, branches par fonctionnalité, relecture croisée.

    C. Architecture envisagée

    Architecture client – serveur avec séparation nette frontend / backend. Le frontend (Single Page Application) appelle l'API REST en JSON ; l'API authentifie, vérifie les droits (RBAC) et applique les règles métier avant d'écrire en base.

    IX. Critères de validation

    Les critères de validation correspondent aux exigences du sujet :

    • Inscription et authentification fonctionnelles.
    • Processus d'inscription aux cours complet, avec règles métier.
    • Ajout / retrait de cours et de données académiques par l'administration.
    • Modération de la plateforme par l'administrateur.
    • Interface claire, ergonomique et responsive.
    • Calcul automatique des moyennes et détermination du résultat (admis / non admis).
    • Sécurité : sessions, CSRF, RBAC, requêtes préparées, hashage des mots de passe.
